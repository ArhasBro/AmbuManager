## 1. Objectif du document
Ce document définit une référence UI/UX codable de la page **Suivi des véhicules** pour reproduction visuelle minimale à 99 % des maquettes V2.  
Il ne constitue pas une validation fonctionnelle définitive : la validation métier finale reste hors de ce document.

<a id="sec-4"></a>
## 4. Rôle de la page Suivi des véhicules
- Nom exact de page : **Suivi des véhicules**.
- Cette page centralise les workflows opérationnels : vérifications, désinfections, anomalies.
- Cette page est distincte de **Véhicules**.
- **Véhicules** garde la gestion flotte et informations administratives.
- **Suivi des véhicules** gère le suivi opérationnel quotidien et les actions de traitement.

<a id="sec-5"></a>
## 5. Objectif UX de la page
- Donner une lecture immédiate de la conformité opérationnelle de la flotte.
- Prioriser ce qui doit être traité maintenant.
- Réduire les erreurs d’action grâce à des statuts et criticités explicites.
- Sécuriser les actions sensibles via permissions visibles et traçabilité.
- Maintenir une densité forte de données sans perdre la lisibilité.

<a id="sec-6"></a>
## 6. Structure générale de l’écran
- Shell applicatif constant : barre latérale gauche, top bar globale, zone contenu principale.
- Zone contenu page : titre + sous-titre + actions principales alignées à droite.
- Bandeau onglets sous l’en-tête.
- Selon onglet : KPI en haut, filtres/recherche, tableau principal, pagination.
- Colonne latérale de support quand visible : rappels, accès rapides, panneau de détail, actions autorisées.

<a id="sec-7"></a>
## 7. Layout desktop attendu
- Référence desktop principale : maquettes en `1672x941`, variante désinfection en `1536x1024`.
- Barre latérale gauche fixe et dominante visuelle de navigation.
- Zone contenu centrée sur une grille large, avec marge intérieure confortable.
- Sur **Vue d’ensemble**, **Vérifications**, **Anomalies** : table large à gauche + colonne droite dédiée.
- Sur **Désinfections** : table pleine largeur et bandeaux de légende/rappel en bas.

<a id="sec-8"></a>
## 8. En-tête de page
- Titre principal visible et constant : **Suivi des véhicules**.
- Sous-titre contextuel différent selon onglet mais même style typographique.
- Actions hautes visibles selon onglet :
- Vue d’ensemble : `Nouvelle vérification`, `Nouvelle désinfection`, `Déclarer une anomalie`.
- Vérifications : `Déclarer une anomalie`, `Nouvelle vérification`.
- Désinfections : `Nouvelle désinfection`.
- Anomalies : `Exporter la liste`, `Déclarer une anomalie`.
- Style bouton principal : plein bleu, texte blanc, rayon arrondi, icône à gauche.
- Style bouton secondaire : fond blanc, bord fin, texte foncé, icône à gauche.

<a id="sec-9"></a>
## 9. Navigation par onglets
- Ordre figé : `Vue d’ensemble`, `Vérifications`, `Désinfections`, `Anomalies des véhicules`.
- Onglet actif : texte bleu + soulignement bleu net.
- Onglet inactif : texte foncé atténué, sans fond.
- Ligne de séparation horizontale sous les onglets.
- Aucun onglet `Entretien` en Alpha.

<a id="sec-10"></a>
## 10. Logique commune des onglets
- Même architecture visuelle pour garder les repères utilisateur.
- Les actions créatives sont en haut à droite, jamais dans la barre latérale.
- Tous les tableaux portent pagination et contrôle `Lignes par page`.
- Les actions sensibles ne sont jamais implicites.
- La disponibilité véhicule n’est jamais modifiée automatiquement par un résultat de suivi.
- Les éléments de traçabilité sont visibles dans le détail ou via accès autorisé.

<a id="sec-11"></a>
## 11. Vue d’ensemble
- Objectif : piloter les éléments à traiter immédiatement.
- En haut : 5 cartes KPI de synthèse.
- Centre gauche : carte `Véhicules à traiter` avec filtres et table.
- Centre droit : carte `Rappels importants`.
- Bas droit : carte `Accès rapides` avec entrées orientées action.
- Table orientée traitement, pas historique exhaustif.

<a id="sec-12"></a>
## 12. KPI et synthèses de suivi
- Vue d’ensemble affiche :
- `Véhicules suivis`.
- `Vérifications à faire`.
- `Désinfections à faire`.
- `Anomalies ouvertes`.
- `Véhicules indisponibles`.
- Désinfections affiche :
- `Désinfections totales`.
- `En attente de contre-vérification`.
- `Contre-vérifiées`.
- `Refusées / à reprendre`.
- Anomalies affiche :
- `Anomalies ouvertes`.
- `Bloquantes`.
- `Majeures`.
- `Véhicules indisponibles`.
- Les sous-lignes de KPI mettent en avant les volumes critiques en rouge.

<a id="sec-13"></a>
## 13. Cartes véhicules suivis
- Les cartes KPI sont des cartes blanches bordées, rayon moyen, ombre très légère.
- Chaque carte contient :
- Icône ronde colorée à gauche.
- Libellé métier en haut.
- Valeur principale volumineuse.
- Sous-information (retard, criticité, pourcentage ou portée).
- La carte `Véhicules suivis` est informative.
- Les cartes `à faire`, `ouvertes`, `indisponibles` expriment la priorité opérationnelle.

<a id="sec-14"></a>
## 14. Alertes et éléments à traiter
- Vue d’ensemble : `Rappels importants` liste explicitement :
- aucune indisponibilité automatique ;
- changement de disponibilité sur action explicite autorisée ;
- motif obligatoire.
- Désinfections : bandeau jaune `en attente de contre-vérification` avec action `Voir la liste`.
- Vérifications : bandeau bleu rappel `2 vérificateurs` pour ambulance.
- Anomalies : panneau info en bas rappelant l’interdiction d’indisponibilité automatique.

<a id="sec-15"></a>
## 15. Onglet Vérifications
- En-tête onglet orienté contrôle quotidien.
- Bandeau de règle métier immédiatement visible avant les filtres.
- Table principale `Liste des vérifications`.
- Panneau droit `Détail de la vérification`.
- Le panneau détail affiche contexte + bouton de déclaration d’anomalie si nécessaire.

<a id="sec-16"></a>
## 16. Tableau des vérifications
- Colonnes visibles en maquette :
- `Véhicule`.
- `Type`.
- `Base / dépôt`.
- `Date de vérification`.
- `Vérificateur 1`.
- `Vérificateur 2`.
- `Résultat`.
- `Anomalie liée`.
- `Actions`.
- Le champ `Vérificateur 2` est réellement présent et utile en ambulance.
- Les actions de ligne sont au minimum `Consulter` (œil) + menu complémentaire.

<a id="sec-17"></a>
## 17. Création d’une vérification
- Déclenchée par le bouton `Nouvelle vérification`.
- Champs à documenter pour futur codage :
- véhicule ;
- date/heure ;
- vérificateur 1 ;
- vérificateur 2 si type `AMBULANCE` ;
- résultat ;
- commentaire ;
- anomalie détectée oui/non.
- Règle de saisie :
- `AMBULANCE` requiert 2 vérificateurs.
- autres types requièrent 1 vérificateur.
- En cas d’anomalie, la vérification est enregistrée puis l’action `Déclarer une anomalie` est proposée.

<a id="sec-18"></a>
## 18. Résultats de vérification
- Résultats autorisés :
- `Conforme` ;
- `Non conforme` ;
- `Sous réserve` ;
- `À vérifier`.
- Mapping métier obligatoire :
- `Conforme` = pas d’anomalie.
- `Non conforme` = anomalie bloquante.
- `Sous réserve` = anomalie non bloquante.
- `À vérifier` = anomalie non bloquante.
- Aucun de ces résultats ne doit provoquer une indisponibilité automatique.

<a id="sec-19"></a>
## 19. Vérification quotidienne non faite
- Fréquence attendue : quotidienne.
- Si non faite, génération d’une anomalie `majeure` d’office.
- La génération automatique de cette anomalie n’implique pas indisponibilité automatique.
- Le passage indisponible reste une action explicite réservée aux profils autorisés.
- Cette règle doit être visible en UX dans les rappels/bandeaux et en traçabilité.

<a id="sec-20"></a>
## 20. Onglet Désinfections
- En-tête orienté hygiène/entretien opérationnel.
- KPI dédiés à la chaîne `réalisée -> contre-vérifiée -> refusée`.
- Barre de filtres enrichie avec bouton `Filtres`.
- Bandeau d’alerte prioritaire sur les éléments en attente de contre-vérification.
- Table principale `Liste des désinfections`.
- Légendes explicatives et bloc d’accès à la contre-vérification en bas d’écran.

<a id="sec-21"></a>
## 21. Tableau des désinfections
- Colonnes visibles en maquette :
- `Véhicule` (photo + identité).
- `Type`.
- `Base / dépôt`.
- `Date de désinfection`.
- `Type de désinfection`.
- `Produit utilisé`.
- `Réalisée par`.
- `Résultat`.
- `Contre-vérification`.
- `Anomalie liée`.
- `Actions`.
- La colonne `Contre-vérification` contient statut + horodatage + contre-vérificateur quand présent.
- La colonne `Anomalie liée` accepte un code d’anomalie ou `—`.

<a id="sec-22"></a>
## 22. Création d’une désinfection
- Déclenchée par `Nouvelle désinfection`.
- Champs à documenter pour futur codage :
- véhicule ;
- date/heure ;
- type de désinfection ;
- produit utilisé ;
- opérateur ;
- résultat ;
- commentaire ;
- problème constaté oui/non.
- Si problème constaté, proposer `Déclarer une anomalie`.
- Éléments type preuve mobile/signature : hors Alpha si non visibles en maquette.

<a id="sec-23"></a>
## 23. Contre-vérification désinfection
- Réservée à `Admin`, `Gérant` ou utilisateur explicitement autorisé.
- Non accessible à un utilisateur terrain non autorisé.
- Le contre-vérificateur doit être différent du déclarant/réalisateur.
- Statuts visuels à conserver :
- `En attente`.
- `Contre-vérifiée`.
- `Refusée / à reprendre`.
- Les rappels d’autorisation doivent rester visibles dans l’onglet.

<a id="sec-24"></a>
## 24. Onglet Anomalies des véhicules
- Vue orientée pilotage des incidents et de leur traitement.
- KPI concentrés sur `ouvertes`, `bloquantes`, `majeures`, `indisponibles`.
- Table centrale dense et priorisée par statuts/criticités.
- Panneau droit détaillé avec actions de traitement et actions de disponibilité.
- Bouton `Exporter la liste` visible en action secondaire.

<a id="sec-25"></a>
## 25. Tableau des anomalies
- Colonnes visibles :
- `Véhicule`.
- `Type de véhicule`.
- `Source`.
- `Date du constat`.
- `Déclarant`.
- `Criticité`.
- `Statut`.
- `Disponibilité actuelle`.
- `Actions`.
- Les badges de criticité/statut sont systématiques.
- Les sources sont distinguées par badges.
- Les actions de ligne restent compactes : œil + menu.

<a id="sec-26"></a>
## 26. Déclaration d’une anomalie
- Déclenchée par `Déclarer une anomalie` depuis l’en-tête ou depuis un flux lié.
- Champs à documenter pour futur codage :
- véhicule ;
- date/heure du constat ;
- déclarant ;
- source ;
- criticité ;
- description/constat ;
- liens éventuels avec vérification/désinfection.
- Après enregistrement :
- l’anomalie apparaît dans l’onglet Anomalies ;
- les actions de traitement sont conditionnées aux permissions.

<a id="sec-27"></a>
## 27. Sources d’anomalies
- Sources autorisées :
- déclaration manuelle ;
- vérification ;
- désinfection ;
- vérification quotidienne non faite ;
- autre.
- Représentation UI : badge source lisible dans tableau et panneau détail.

<a id="sec-28"></a>
## 28. Statuts d’anomalies
- Statuts autorisés :
- `ouverte` ;
- `en cours de traitement` ;
- `résolue` ;
- `annulée / classée sans suite`.
- Représentation UI :
- badge couleur + libellé explicite.
- Aucune suppression physique en Alpha.

<a id="sec-29"></a>
## 29. Criticités d’anomalies
- Criticités autorisées :
- `non bloquante` ;
- `bloquante` ;
- `majeure`.
- Représentation UI :
- `non bloquante` en tonalité positive/neutre ;
- `bloquante` en tonalité rouge ;
- `majeure` en tonalité orange.
- La criticité est visible dans table + détail + KPI dédiés.

<a id="sec-30"></a>
## 30. Changement de disponibilité véhicule
- Changement `Disponible / Indisponible` sur action explicite uniquement.
- Action réservée à `Admin`, `Gérant` ou utilisateur autorisé.
- Motif obligatoire à la mise en indisponible et au retour disponible.
- Aucune indisponibilité automatique issue de vérification, désinfection ou anomalie.
- Toute action de disponibilité doit être tracée dans l’audit.

<a id="sec-31"></a>
## 31. Panneaux de détail
- Vérifications : panneau droit `Détail de la vérification` avec identité véhicule, contexte de contrôle, résultat, anomalie détectée, action de déclaration.
- Anomalies : panneau droit `Détail de l’anomalie` avec source, criticité, statut, disponibilité, description, liens, actions.
- Vue d’ensemble : colonne droite de guidance (`Rappels importants`, `Accès rapides`).
- Désinfections : pas de panneau droit permanent, logique remplacée par bandeaux et légendes bas.

<a id="sec-32"></a>
## 32. Filtres et recherche
- Présence systématique d’une recherche textuelle par onglet.
- Sélecteurs visibles selon contexte :
- Vue d’ensemble : type, base/dépôt, état de suivi, disponibilité.
- Vérifications : type, base/dépôt, résultat, anomalie liée.
- Désinfections : statut, véhicule, base/dépôt, type de désinfection.
- Anomalies : source, criticité, statut, disponibilité, base/dépôt.
- Bouton `Réinitialiser` visible sur les onglets qui l’utilisent.
- Les filtres sont en ligne unique desktop, avant le tableau.

<a id="sec-33"></a>
## 33. Boutons et actions
- Boutons primaires de création/déclaration en haut à droite.
- Boutons secondaires de support : exporter, réinitialiser, voir la liste.
- Actions de ligne : `Consulter` + menu contextuel.
- Actions de panneau anomalie :
- modifier statut ;
- modifier criticité ;
- passer en cours de traitement ;
- résoudre ;
- classer sans suite ;
- rendre indisponible ;
- remettre disponible ;
- voir vérification liée ;
- voir désinfection liée.
- Toute action sensible non autorisée doit être masquée ou désactivée.

<a id="sec-34"></a>
## 34. Badges et statuts visuels
- Badges de type véhicule : `AMBULANCE`, `VSL`, `TAXI`, `TPMR`.
- Badges de résultat vérification : `Conforme`, `Non conforme`, `Sous réserve`, `À vérifier`.
- Badges de résultat désinfection : `Réalisée`, `Réalisée avec réserve`, `Non réalisée`, `À refaire`.
- Badges d’état de suivi : `OK`, `À vérifier`, `À désinfecter`, `Anomalie ouverte`.
- Badges disponibilité : `Disponible`, `Indisponible`.
- Badges anomalie : source, criticité, statut.
- Forme visuelle attendue : pastille/pilule à fond léger et texte coloré lisible.

<a id="sec-35"></a>
## 35. Icônes et pictogrammes
- Icônes d’actions : plus, alerte, œil, menu, reset, filtre, export.
- Icônes de statut/KPI : bouclier, horloge, check, croix, point d’exclamation, disponibilité.
- Icônes de navigation shell : cohérence de trait et taille.
- Usage constant :
- icône avant libellé dans les boutons ;
- icône dans cercle coloré pour KPI ;
- icône d’information sur bandeaux et rappels.

<a id="sec-36"></a>
## 36. États visuels à prévoir
- `Loading` page : skeleton/cartes/table lisibles sans décalage.
- `Empty` global : aucun véhicule suivi.
- `Empty` local : aucun résultat après filtres.
- `Erreur` : chargement impossible avec action de relance.
- `Accès refusé` : sur action ou accès direct non autorisé.
- `Action indisponible` : bouton masqué ou disabled selon permission.
- `Alerte opérationnelle` : vérification quotidienne non faite, contre-vérification en attente.

<a id="sec-37"></a>
## 37. Hiérarchie visuelle
- Niveau 1 : titre page + actions primaires.
- Niveau 2 : onglet actif.
- Niveau 3 : KPI synthèse.
- Niveau 4 : filtres/recherche.
- Niveau 5 : tableau de données.
- Niveau 6 : panneaux contextuels, rappels et accès rapides.
- Les éléments critiques utilisent accent couleur chaude + libellé explicite.

<a id="sec-38"></a>
## 38. Espacements dimensions et densité
- Les maquettes montrent une grille régulière à densité intermédiaire/élevée.
- Cibles visuelles desktop observées :
- padding externe contenu autour de 24 px ;
- espaces inter-blocs autour de 16 à 24 px ;
- cartes KPI avec padding interne autour de 20 à 24 px ;
- contrôles de filtre hauteur homogène ;
- lignes de tableau compactes mais respirantes ;
- rayons cohérents sur cartes, inputs, boutons et badges.
- Exigence de reproduction : conserver les proportions entre blocs, pas seulement les composants isolés.

<a id="sec-39"></a>
## 39. Couleurs et ambiance visuelle
- Ambiance générale : fond clair, cartes blanches, bordures très fines.
- Couleur d’accent principale : bleu interface (actions primaires, onglet actif, liens).
- États positifs : vert.
- États de vigilance : orange/jaune.
- États critiques : rouge.
- États neutres/information : bleu clair/gris.
- Interdiction : inversion de thème ou changement de palette non prévu par maquette dans ce scope.

<a id="sec-40"></a>
## 40. Typographie
- Hiérarchie visible :
- titre page fort et large ;
- sous-titre secondaire lisible ;
- titres de cartes/tableaux intermédiaires ;
- contenu tableau compact et lisible ;
- badges en corps réduit mais contrasté.
- Les chiffres KPI doivent rester visuellement dominants.
- Le poids de police doit distinguer données critiques sans surcharge.

<a id="sec-41"></a>
## 41. Règles de permissions visibles
- `Admin` et `Gérant` : droits Alpha complets.
- Utilisateurs terrain : consultation + création vérifications/désinfections + déclaration anomalie.
- Contre-vérification désinfection : réservée aux profils autorisés.
- Changement statut/criticité/résolution/classement anomalie : réservé profils autorisés.
- Changement disponibilité : réservé profils autorisés avec motif obligatoire.
- Si non autorisé :
- action masquée ou désactivée ;
- accès direct forcé renvoie `Accès refusé`.

<a id="sec-42"></a>
## 42. Règles d’ergonomie métier
- Ne pas confondre flux `saisir` et flux `traiter`.
- Rendre immédiatement visibles les urgences :
- retards ;
- anomalies ouvertes ;
- bloquantes/majeures ;
- indisponibilités.
- Garder les actions sensibles près du détail concerné.
- Limiter les clics inutiles pour l’utilisateur terrain.
- Exposer les conséquences métier via rappels clairs.

<a id="sec-46"></a>
## 46. Accessibilité minimale
- Ordre de tabulation logique : en-tête -> onglets -> filtres -> table -> détail.
- Focus visible sur boutons, tabs, inputs, menus d’actions.
- Libellés explicites sur icônes seules (`aria-label` à prévoir au codage).
- Contraste texte/fond suffisant pour statuts colorés.
- Ne pas véhiculer l’information uniquement par la couleur.
- États disabled explicitement différenciés.

<a id="sec-47"></a>

- Intégration complète des formulaires de création (vérification, désinfection, anomalie).

<a id="sec-48"></a>
## 48. Ce qui ne doit pas être codé
- Suppression physique d’anomalie.
- Indisponibilité automatique véhicule.
- Contre-vérification accessible à tous.
- Signature électronique en Alpha.
- Preuve mobile en Alpha.
- Maintenance avancée / onglet Entretien en Alpha.
- Géolocalisation.
- Suivi temps réel.
- Régulation.
- Facturation.
- Paie.
- Debug visible.
- JSON visible.
- Contournement des permissions.
