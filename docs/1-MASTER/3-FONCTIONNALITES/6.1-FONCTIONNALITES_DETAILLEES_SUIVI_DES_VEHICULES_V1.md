## 1. Objectif de la page

La page **Suivi des véhicules** permet de suivre l'état opérationnel des véhicules de la société.

Elle complète la page **Véhicules**, mais ne la remplace pas.

La page **Véhicules** reste le référentiel administratif de la flotte.  
La page **Suivi des véhicules** porte les workflows opérationnels liés :

- aux vérifications ;
- aux désinfections ;
- aux anomalies des véhicules ;
- à la synthèse de suivi des véhicules.

Elle doit permettre de savoir rapidement :

- quels véhicules sont à jour ;
- quels véhicules doivent être vérifiés ;
- quels véhicules doivent être désinfectés ;
- quels véhicules présentent une anomalie ;
- quelles anomalies sont ouvertes ;
- quelles actions sont à traiter ;
- si un véhicule est disponible ou indisponible.

La page doit rester exploitable par les équipes terrain, tout en respectant les permissions et la traçabilité des actions sensibles.

## 2. Positionnement fonctionnel

### 2.1 Page Véhicules

La page **Véhicules** reste le référentiel administratif de la flotte.

Elle contient les informations stables du véhicule :

- nom interne ;
- marque ;
- modèle ;
- type de véhicule ;
- immatriculation ;
- statut administratif ;
- disponibilité générale ;
- base / dépôt principal ;
- commentaire interne simple si utile.

Elle peut afficher un résumé de suivi, mais elle ne porte pas les workflows détaillés.

### 2.2 Page Suivi des véhicules

La page **Suivi des véhicules** est une page opérationnelle.

Elle contient les workflows liés :

- aux contrôles réguliers ;
- aux désinfections ;
- aux anomalies ;
- à la consultation de l'état de suivi.

Elle ne doit pas modifier directement :

- la marque ;
- le modèle ;
- l'immatriculation ;
- le type administratif du véhicule ;
- la base / dépôt principal ;
- les informations générales du référentiel véhicule.

Ces informations restent gérées dans la page **Véhicules**.

### 2.3 Séparation des responsabilités

La séparation attendue est la suivante :

```text
Véhicules
= référentiel administratif de flotte

Suivi des véhicules
= suivi opérationnel, sanitaire, anomalies et actions terrain
```

Cette séparation permet de garder les pages lisibles et d'éviter de mélanger les informations administratives avec les actions opérationnelles quotidiennes.

## 3. Base de cadrage fonctionnel V1 / Alpha
La page **Suivi des véhicules V1 / Alpha** est composée de quatre onglets :

1. Vue d'ensemble ;
2. Vérifications ;
3. Désinfections ;
4. Anomalies des véhicules.

L'onglet **Entretiens des véhicules** est prévu au minimum pour la Beta.  
Il ne fait pas partie du périmètre V1 / Alpha.

Fonctionnalités cibles de référence pour la V1 / Alpha (à confirmer) :

- consultation d'une vue d'ensemble du suivi des véhicules ;
- consultation des vérifications ;
- création d'une vérification ;
- consultation des désinfections ;
- création d'une désinfection ;
- contre-vérification d'une désinfection par un tiers autorisé différent ;
- consultation des anomalies des véhicules ;

- modification de la criticité d'une anomalie selon permissions ;

- traçabilité audit des actions sensibles ;

## 4. Organisation des onglets

### 4.1 Onglets V1 / Alpha

#### Anomalies des véhicules

## 5. Vue d'ensemble

### 5.1 Objectif

La **Vue d'ensemble** est l'écran d'entrée de la page **Suivi des véhicules**.

Elle doit permettre de comprendre rapidement l'état opérationnel du parc suivi.

Elle ne doit pas remplacer les onglets détaillés.

Son rôle est de répondre rapidement aux questions suivantes :

```text
Quels véhicules sont OK 
Quels véhicules nécessitent une action 
Quels véhicules ont une anomalie ouverte 
Quels véhicules doivent être vérifiés 
Quels véhicules doivent être désinfectés 
Quels véhicules sont indisponibles 
```

### 5.2 Tuiles de synthèse

La Vue d'ensemble affiche des tuiles simples.

Tuiles validées en V1 / Alpha :

- véhicules suivis ;
- vérifications à faire ;
- désinfections à faire ;
- anomalies ouvertes ;
- véhicules indisponibles.

### 5.3 Véhicules suivis

La tuile **Véhicules suivis** affiche le nombre de véhicules actifs et non archivés concernés par le suivi.

Les véhicules archivés ne sont pas affichés par défaut.

Les véhicules inactifs ne sont pas affichés par défaut dans la Vue d'ensemble opérationnelle.

Ils restent consultables depuis la page **Véhicules** selon permissions.

### 5.4 Vérifications à faire

La tuile **Vérifications à faire** affiche les véhicules dont la vérification quotidienne est attendue ou non réalisée.

Une vérification quotidienne non réalisée doit générer une anomalie majeure d'office.

### 5.5 Désinfections à faire

La tuile **Désinfections à faire** affiche les véhicules dont une désinfection est attendue selon les règles applicables.

Les règles exactes de déclenchement dépendent notamment :

- de la règle quotidienne ;
- de l'utilisation du véhicule ;
- du type de transport ;
- d'une action manuelle ;
- des règles ARS à confirmer.

### 5.6 Anomalies ouvertes

La tuile **Anomalies ouvertes** affiche le nombre d'anomalies non résolues.

Elle peut inclure :

- anomalies non bloquantes ;
- anomalies bloquantes ;
- anomalies majeures.

### 5.7 Véhicules indisponibles

La tuile **Véhicules indisponibles** affiche les véhicules dont la disponibilité générale est actuellement indisponible.

Un véhicule peut être indisponible uniquement après action explicite autorisée.

Aucune vérification, désinfection ou anomalie ne rend automatiquement un véhicule indisponible.

### 5.8 Tableau "Véhicules à traiter"

La Vue d'ensemble contient un tableau principal :

```text
Véhicules à traiter
```

Ce tableau affiche uniquement les véhicules nécessitant une action.

Colonnes proposées :

- véhicule ;
- type ;
- base / dépôt ;
- dernière vérification ;
- dernière désinfection ;
- anomalie ouverte ;
- état de suivi ;
- disponibilité actuelle ;
- actions.

Exemple :

```text
AMBULANCE 01
AMBULANCE
Lamballe
À vérifier
OK
1 anomalie ouverte
À traiter
Disponible
```

### 5.9 États de suivi

États simples affichables dans la Vue d'ensemble :

- OK ;
- à vérifier ;
- à désinfecter ;
- anomalie ouverte ;
- à traiter ;
- indisponible.

Un véhicule peut cumuler plusieurs sujets, mais la Vue d'ensemble affiche un état prioritaire.

Priorité d'affichage proposée :

```text
1. Indisponible
2. Anomalie ouverte
3. À vérifier
4. À désinfecter
5. OK
```

### 5.10 Actions rapides

Actions possibles depuis la Vue d'ensemble :

- voir le suivi du véhicule ;
- aller aux vérifications ;
- aller aux désinfections ;
- déclarer une anomalie ;
- voir les anomalies ouvertes.

La Vue d'ensemble ne doit pas permettre de valider directement une vérification ou une désinfection.

Les actions d'enregistrement doivent rester dans les onglets détaillés.

### 5.11 Filtres simples

Filtres prévus en V1 / Alpha :

- recherche par nom interne ;
- recherche par immatriculation ;
- type de véhicule ;
- base / dépôt ;
- état de suivi ;
- disponibilité générale.

Pas de filtre avancé en Alpha.

## 6. Vérifications

### 6.1 Objectif

L'onglet **Vérifications** sert à enregistrer les vérifications quotidiennes des véhicules.

Il doit permettre de savoir :

- quel véhicule a été vérifié ;
- quand il a été vérifié ;
- par qui il a été vérifié ;
- quel est le résultat ;
- si une anomalie est constatée ;
- si la vérification est conforme ou non.

### 6.2 Règles ARS

Les vérifications véhicules reposent sur des règles obligatoires précises délivrées par l'ARS.

Le détail exact des points de contrôle ARS reste à confirmer à partir du document officiel.

En V1 / Alpha, la structure doit permettre de recevoir ces règles, mais le contenu détaillé ne doit pas être inventé.

Mention obligatoire tant que le document officiel n'est pas fourni :

```text
INFORMATION NON FOURNIE — À CONFIRMER
```

### 6.3 Nombre de vérificateurs

Règle validée :

```text
AMBULANCE = 2 vérificateurs
VSL = 1 vérificateur
TAXI = 1 vérificateur
TPMR = 1 vérificateur
```

Une vérification d'ambulance ne doit pas être considérée complète si les deux vérificateurs attendus ne sont pas renseignés.

### 6.4 Résultats possibles

Résultats validés :

- Conforme ;
- Non conforme ;
- Sous réserve ;
- À vérifier.

### 6.5 Résultat Conforme

```text
Conforme
= pas d'anomalie.
```

La vérification est conforme.

Aucune anomalie n'est signalée.

Le véhicule peut rester exploitable si ses autres statuts le permettent.

### 6.6 Résultat Non conforme

```text
Non conforme
= anomalie bloquante.
```

La vérification est non conforme.

Une anomalie bloquante est constatée.

Le véhicule ne devrait pas être utilisé normalement tant que l'anomalie bloquante n'est pas traitée.

Cependant, le véhicule ne passe pas automatiquement en indisponible.

### 6.7 Résultat Sous réserve

```text
Sous réserve
= anomalie non bloquante.
```

La vérification est réalisée avec une réserve.

Une anomalie non bloquante est constatée.

Le véhicule peut rester exploitable, mais le point doit être suivi.

### 6.8 Résultat À vérifier

```text
À vérifier
= anomalie non bloquante.
```

La vérification signale un point à contrôler ou confirmer.

Une anomalie non bloquante peut être déclarée.

Un contrôle complémentaire est nécessaire.

### 6.9 Fréquence

La vérification est quotidienne.

Règles validées :

- une vérification quotidienne est attendue ;
- l'application ne bloque pas automatiquement si la vérification n'est pas faite ;
- une vérification quotidienne non faite génère une anomalie majeure d'office.

### 6.10 Anomalie liée à une vérification

Option validée :

```text
Option B :
La vérification est enregistrée.
Puis l'utilisateur est orienté vers l'action "Déclarer une anomalie".
```

La création complète de l'anomalie ne doit pas être mélangée dans le formulaire de vérification.

L'onglet **Anomalies des véhicules** prend le relais pour la déclaration et le suivi détaillé.

### 6.11 Formulaire de création d'une vérification

Champs attendus :

- véhicule concerné ;
- date / heure de vérification ;
- vérificateur 1 ;
- vérificateur 2 si véhicule de type AMBULANCE ;
- résultat de la vérification ;
- commentaire optionnel ;
- anomalie détectée : oui / non.

Si une anomalie est détectée, l'utilisateur doit être orienté vers l'action :

```text
Déclarer une anomalie
```

### 6.12 Liste des vérifications

Colonnes proposées :

- véhicule ;
- type ;
- base / dépôt ;
- date de vérification ;
- vérificateur 1 ;
- vérificateur 2 si applicable ;
- résultat ;
- anomalie liée ;
- actions.

### 6.13 Impact sur la disponibilité

Une vérification non conforme ne modifie pas automatiquement la disponibilité générale du véhicule.

Même en cas d'anomalie bloquante, le passage en indisponible reste une action explicite réservée à :

- Admin ;
- Gérant ;
- utilisateur autorisé.

## 7. Désinfections

### 7.1 Objectif

L'onglet **Désinfections** sert à enregistrer, consulter et contre-vérifier les désinfections des véhicules.

Il doit permettre de savoir :

- quel véhicule a été désinfecté ;
- quand la désinfection a été réalisée ;
- par qui elle a été réalisée ;
- quel produit a été utilisé ;
- quel est le résultat ;
- si une contre-vérification est nécessaire ou réalisée ;
- si une anomalie doit être déclarée.

### 7.2 Règles ARS

Les désinfections véhicules sont soumises à des règles obligatoires définies par l'ARS.

Le détail exact des protocoles, produits, fréquences et niveaux de contrôle reste à confirmer à partir du document officiel.

Mention obligatoire tant que le document officiel n'est pas fourni :

```text
INFORMATION NON FOURNIE — À CONFIRMER
```

### 7.3 Déclencheurs de désinfection

Les désinfections peuvent être attendues selon plusieurs déclencheurs :

- quotidiennement ;
- après chaque utilisation ou transport ;
- après certains transports spécifiques ;
- manuellement selon besoin ou décision interne.

La désinfection n'est donc pas limitée à une fréquence unique.

Le détail exact des cas imposant une désinfection reste à confirmer avec le document ARS.

### 7.4 Type de produit utilisé

Le formulaire de désinfection doit inclure le type de produit utilisé.

Le niveau exact d'obligation du champ dépendra des règles ARS à confirmer.

En Alpha, le champ doit être prévu dans le formulaire.

### 7.5 Résultats possibles

Résultats validés :

- Réalisée ;
- Réalisée avec réserve ;
- Non réalisée ;
- À refaire.

### 7.6 Résultat Réalisée

La désinfection est réalisée sans réserve.

Aucun point complémentaire n'est signalé.

### 7.7 Résultat Réalisée avec réserve

La désinfection est réalisée, mais un point doit être surveillé.

Le point à surveiller doit être renseigné obligatoirement.

### 7.8 Résultat Non réalisée

La désinfection attendue n'a pas été réalisée.

Un motif doit être renseigné obligatoirement.

### 7.9 Résultat À refaire

La désinfection réalisée est jugée insuffisante ou non conforme.

Un motif doit être renseigné obligatoirement.

### 7.10 Contre-vérification

Une désinfection doit faire l'objet d'une contre-vérification par un tiers autorisé.

Le contre-vérificateur doit être différent du ou des utilisateurs ayant réalisé la désinfection.

La contre-vérification est réservée à :

- Admin ;
- Gérant ;
- utilisateur autorisé.

Elle ne peut pas être réalisée par n'importe quel utilisateur terrain différent.

### 7.11 Statuts de contre-vérification

Statuts possibles :

- en attente de contre-vérification ;
- contre-vérifiée ;
- refusée / à reprendre.

Une désinfection enregistrée reste en état **En attente de contre-vérification** tant qu'un tiers autorisé différent ne l'a pas contrôlée.

### 7.12 Formulaire de création d'une désinfection

Champs attendus :

- véhicule concerné ;
- date / heure de désinfection ;
- utilisateur ayant réalisé la désinfection ;
- type de désinfection ;
- type de produit utilisé ;
- résultat ;
- point à surveiller si résultat `Réalisée avec réserve` ;
- motif si résultat `Non réalisée` ;
- motif si résultat `À refaire` ;
- commentaire optionnel ;
- problème constaté : oui / non.

Si un problème est constaté, l'utilisateur doit être orienté vers l'action :

```text
Déclarer une anomalie
```

### 7.13 Liste des désinfections

Colonnes proposées :

- véhicule ;
- type ;
- base / dépôt ;
- date de désinfection ;
- type de désinfection ;
- produit utilisé ;
- réalisée par ;
- résultat ;
- contre-vérification ;
- anomalie liée ;
- actions.

### 7.14 Impact sur la disponibilité

Une désinfection non réalisée, réalisée avec réserve, à refaire ou non contre-vérifiée ne rend pas automatiquement le véhicule indisponible.

Le passage en indisponible reste une action explicite réservée à :

- Admin ;
- Gérant ;
- utilisateur autorisé.

## 8. Anomalies des véhicules

### 8.1 Objectif

L'onglet **Anomalies des véhicules** centralise les anomalies liées aux véhicules.

Il doit permettre de :

- déclarer une anomalie ;
- consulter les anomalies ouvertes ;
- consulter les anomalies résolues ou classées si autorisé ;
- qualifier une anomalie ;
- suivre son statut ;
- rattacher l'anomalie à une vérification ou une désinfection si applicable ;
- traiter l'anomalie selon permissions.

### 8.2 Sources d'anomalie

Sources validées :

- déclaration manuelle ;
- vérification ;
- désinfection ;
- vérification quotidienne non faite ;
- autre.

### 8.3 Criticités

Criticités validées :

- non bloquante ;
- bloquante ;
- majeure.

### 8.4 Anomalie non bloquante

Une anomalie non bloquante signale un problème à suivre.

Le véhicule peut rester exploitable si ses autres statuts le permettent.

### 8.5 Anomalie bloquante

Une anomalie bloquante signale un problème important.

Le véhicule ne devrait pas être utilisé normalement tant que le problème n'est pas traité.

Cependant, même une anomalie bloquante ne rend pas automatiquement le véhicule indisponible.

### 8.6 Anomalie majeure

Une anomalie majeure signale un manquement ou un problème important devant être visible et traité.

Une vérification quotidienne non faite génère une anomalie majeure d'office.

### 8.7 Statuts d'une anomalie

Statuts validés :

- ouverte ;
- en cours de traitement ;
- résolue ;
- annulée / classée sans suite.

### 8.8 Statut Ouverte

L'anomalie est déclarée et non traitée.

### 8.9 Statut En cours de traitement

Une action est en cours.

L'anomalie n'est pas encore clôturée.

### 8.10 Statut Résolue

L'anomalie a été traitée et clôturée par un utilisateur autorisé.

### 8.11 Statut Annulée / classée sans suite

L'anomalie a été créée par erreur ou n'est finalement pas retenue.

Ce statut évite la suppression physique.

### 8.12 Lien avec les vérifications

Règles validées :

```text
Résultat Conforme
= aucune anomalie.

Résultat Non conforme
= anomalie bloquante.

Résultat Sous réserve
= anomalie non bloquante.

Résultat À vérifier
= anomalie non bloquante.

Vérification quotidienne non faite
= anomalie majeure d'office.
```

### 8.13 Lien avec les désinfections

Une désinfection peut entraîner une anomalie ou un point à traiter.

Règles de principe :

```text
Réalisée
= aucune anomalie obligatoire.

Réalisée avec réserve
= point à surveiller obligatoire.

Non réalisée
= motif obligatoire et anomalie possible selon contexte.

À refaire
= motif obligatoire et anomalie possible selon contexte.
```

L'option retenue reste la même que pour les vérifications :

```text
La désinfection est enregistrée.
Puis l'utilisateur est orienté vers "Déclarer une anomalie" si le résultat le nécessite.
```

### 8.14 Formulaire de déclaration d'une anomalie

Champs attendus :

- véhicule concerné ;
- date / heure du constat ;
- déclarant ;
- source de l'anomalie ;
- titre court ;
- description ;
- criticité ;
- lien avec une vérification si applicable ;
- lien avec une désinfection si applicable ;
- commentaire ou action immédiate proposée.

### 8.15 Liste des anomalies

Colonnes proposées :

- véhicule ;
- type de véhicule ;
- source ;
- date du constat ;
- déclarant ;
- criticité ;
- statut ;
- disponibilité actuelle du véhicule ;
- actions.

### 8.16 Actions disponibles

Actions possibles selon permissions :

- consulter ;
- déclarer une anomalie ;
- modifier le statut ;
- modifier la criticité ;
- passer en cours de traitement ;
- résoudre ;
- classer sans suite ;
- rendre le véhicule indisponible ;
- remettre le véhicule disponible ;
- voir le véhicule ;
- voir la vérification liée ;
- voir la désinfection liée.

### 8.17 Suppression physique

Aucune suppression physique d'anomalie n'est prévue en Alpha.

Une anomalie créée par erreur doit être annulée ou classée sans suite.

## 9. Accès et permissions

### 9.1 Principe général

La page **Suivi des véhicules** est accessible selon les rôles et permissions.

Elle doit permettre aux utilisateurs terrain de participer au suivi quotidien, tout en réservant les actions sensibles aux profils autorisés.

### 9.2 Admin / Gérant

En Alpha, Admin et Gérant disposent de tous les droits sur la page **Suivi des véhicules**.

Ils peuvent :

- consulter la Vue d'ensemble ;
- consulter les vérifications ;
- créer une vérification ;
- consulter les désinfections ;
- créer une désinfection ;
- contre-vérifier une désinfection si tiers différent ;
- consulter les anomalies ;
- déclarer une anomalie ;
- modifier le statut d'une anomalie ;
- modifier la criticité d'une anomalie ;
- passer une anomalie en cours de traitement ;
- résoudre une anomalie ;
- classer une anomalie sans suite ;
- rendre un véhicule indisponible ;
- remettre un véhicule disponible ;
- consulter l'historique de suivi ;
- consulter les éléments résolus ou classés.

### 9.3 Utilisateurs terrain

Les utilisateurs terrain peuvent, par défaut :

- consulter la Vue d'ensemble ;
- consulter les vérifications ;
- créer une vérification ;

## 10. Disponibilité véhicule et actions sensibles

### 10.1 Principe général

Les vérifications, désinfections et anomalies alimentent le suivi opérationnel.

Elles ne modifient pas automatiquement la disponibilité générale d'un véhicule.

Règle validée :

```text
Aucune vérification, désinfection ou anomalie ne rend automatiquement un véhicule indisponible.
```

### 10.2 Passage en indisponible

Le passage d'un véhicule en indisponible est une action explicite.

Elle est réservée à :

- Admin ;
- Gérant ;
- utilisateur autorisé.

En Alpha, cette action nécessite obligatoirement un motif.

Elle doit être tracée dans l'audit.

### 10.3 Remise disponible

La remise d'un véhicule disponible est une action explicite.

Elle est réservée à :

- Admin ;
- Gérant ;
- utilisateur autorisé.

En Alpha, cette action nécessite obligatoirement un motif.

Elle doit être tracée dans l'audit.

### 10.4 Actions critiques

Certaines actions du Suivi des véhicules sont critiques, car elles peuvent avoir un impact sur :

- les salariés / utilisateurs ;
- les patients / personnes transportées ;
- la disponibilité réelle d'un véhicule ;
- la conformité du suivi sanitaire ou opérationnel.

Actions critiques identifiées :

- contre-vérifier une désinfection ;
- déclarer une anomalie ;
- modifier le statut d'une anomalie ;
- modifier la criticité d'une anomalie ;
- résoudre une anomalie ;
- classer une anomalie sans suite ;
- rendre un véhicule indisponible ;
- remettre un véhicule disponible.

En Alpha, ces actions sont soumises à permissions et doivent être tracées dans l'audit.

En Beta ou en version mobile, certaines actions devront être renforcées par :

- message obligatoire ;
- preuve éventuelle ;
- signature électronique ;
- validation via application mobile.

### 10.5 Signature électronique et preuve

La signature électronique, la preuve obligatoire et la validation via application mobile ne font pas partie du périmètre V1 / Alpha.

Elles sont prévues pour la Beta, la version mobile ou une évolution ultérieure.

## 11. Audit et traçabilité

### 11.1 Principe

Les actions sensibles de la page **Suivi des véhicules** doivent être traçables dans l'audit.

L'audit complet reste consultable dans la page **Audit** selon permissions.

La page **Suivi des véhicules** peut afficher un historique simple ou récent si autorisé.

### 11.2 Actions à tracer

Actions à tracer obligatoirement :

- création d'une vérification ;
- vérification non conforme ;
- vérification quotidienne non faite ;
- création d'une désinfection ;
- désinfection non réalisée ;
- désinfection à refaire ;
- contre-vérification d'une désinfection ;
- refus ou reprise après contre-vérification ;
- déclaration d'une anomalie ;
- changement de criticité d'une anomalie ;
- changement de statut d'une anomalie ;
- passage en cours de traitement ;
- résolution d'une anomalie ;
- classement sans suite ;
- changement de disponibilité du véhicule ;

### 11.3 Historique simple

L'historique simple peut afficher :

- date ;
- utilisateur ;
- action réalisée ;
- véhicule concerné ;
- résultat ;

### 11.4 Conservation de l'historique

Aucune suppression physique d'une vérification, désinfection ou anomalie n'est prévue en Alpha.

En cas d'erreur :

- une anomalie peut être classée sans suite ;
- une désinfection peut être marquée à reprendre ;
- une vérification peut être complétée par une nouvelle entrée ;
- l'historique reste conservé.

## 12. États de la page

### 12.1 Chargement initial

Au chargement initial, la page récupère :

- les véhicules actifs et non archivés ;
- les dernières vérifications ;
- les dernières désinfections ;
- les anomalies ouvertes ;
- les droits de l'utilisateur connecté ;
- les éléments à traiter.

Message possible :

```text
Chargement du suivi des véhicules...
```

### 12.2 Aucun véhicule disponible

Si aucun véhicule actif et non archivé n'est disponible :

```text
Aucun véhicule à suivre.
Ajoutez ou réactivez un véhicule depuis la page Véhicules.
```

La création d'un véhicule ne se fait pas depuis la page **Suivi des véhicules**.

### 12.3 Aucun élément à traiter

Dans la Vue d'ensemble, si aucun véhicule ne nécessite d'action :

```text
Aucun élément à traiter.
Les véhicules suivis ne présentent pas d'action immédiate.
```

### 12.4 Vérification quotidienne non faite

Si une vérification quotidienne n'est pas faite :

```text
Vérification quotidienne non réalisée.
Une anomalie majeure doit être générée d'office.
```

L'application ne bloque pas automatiquement l'exploitation.

### 12.5 Désinfection en attente de contre-vérification

Une désinfection non encore contrôlée par un tiers autorisé affiche l'état :

```text
En attente de contre-vérification
```

### 12.6 Anomalie bloquante ouverte

Si une anomalie bloquante est ouverte :

```text
Anomalie bloquante ouverte.
Le véhicule ne devrait pas être utilisé normalement.
```

Le véhicule ne passe pas automatiquement en indisponible.

### 12.7 Accès non autorisé

Si l'utilisateur tente une action non autorisée :

```text
Action non autorisée.
```

Selon les cas, l'action peut aussi être masquée.

### 12.8 Erreur de chargement

En cas d'erreur technique :

```text
Impossible de charger le suivi des véhicules.
Veuillez réessayer.
```
